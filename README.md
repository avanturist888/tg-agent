# tg-agent

Доступ агентов Claude Code к Telegram — только к тем чатам, которые ты сам
разрешил, и без права отправить что-либо без твоего подтверждения (или, в
чатах с автоотправкой, без окна на отмену).

- MCP-сервер `telegram` с инструментами `tg_read_chat`, `tg_search_chat`,
  `tg_draft_message`, `tg_wait_approval` и т.д.
- Белый список чатов в `config/chats.toml` — всё остальное для агента не существует.
- Отправка — кнопкой в Telegram: агент готовит черновик, тебе в бот прилетает
  карточка с точным текстом и кнопками «Отправить» / «Отклонить».
- Автоотправка для доверенных чатов: сообщение уходит само через 30 секунд,
  если агент (или ты — кнопкой «Отменить» в боте) его не отозвал; можно и
  отправить сразу, не дожидаясь окна.
- Окно управления (`bin\tgw.exe gui`): белый список, черновики, настройки,
  состояние и вход, журнал действий.
- Картинки агент видит сам (`tg_view_media`), любые вложения — включая видео
  целиком — скачивает в `data/downloads/` (`tg_download_file`), а файлы может
  отправлять вместе с сообщением: они приходят тебе в бот рядом с карточкой.
- Реакции агент ставит сразу, без одобрения, но только в чатах с `send = true`;
  каждая пишется в аудит, выключаются целиком `TG_REACTIONS=off` в `.env`.
- Подписка на чаты: служба получает новые сообщения от Telegram сразу и
  дописывает их id в `data/feeds/<alias>.ids`. Подписавшегося агента
  (`tg_subscribe`) служба будит сама — через входящий канал его сессии Claude
  Code (cross-session messaging; подписки — в `data/subscriptions.json`).
  Если агент работает в T3 Code и T3 уже остановил его простаивающую сессию,
  служба будит тред через API T3 (сама выпускает токен с доступом только к
  тредам — в списке сессий T3 он подписан `tg-agent`). Без T3 Code этот путь
  просто не используется.
  Запасной путь — `tg watch <alias>` через Monitor. Telegram агенты сами не
  опрашивают.
- Агенты в контейнерах со своим сервером T3 Code: инструменты — по HTTP с
  токеном агента и его собственным списком чатов, а пробуждение — через треды
  «TG: <чат>», которые служба сама заводит и будит в окружении T3 (см.
  «Агенты в контейнерах»).
- Профили: второй аккаунт Telegram на той же установке со своими сессией,
  чатами, данными и службой (`tg --profile work …`, см. «Профили»). Агенты
  видят все аккаунты через один MCP-сервер `telegram`, карточки всех
  аккаунтов приходят в один бот; к аккаунтам можно оставлять заметки.
- Голосовые и кружки агент получает расшифрованными — встроенной функцией
  Telegram (Premium), с кэшем в `data/transcripts.json`.
- Сессия Telegram лежит локально в `data/session.json`, аудит всех действий —
  в `data/audit.jsonl`.
- Инструкция для агентов: [AGENTS.md](AGENTS.md).

Написано на Go, собирается в один бинарник: `bin\tg.exe` (CLI и MCP-сервер) и
`bin\tgw.exe` (то же, но без окна консоли — для службы и окна управления).
В Telegram ходит служба `tg-agent` с одним постоянным соединением; агенты,
CLI и окно обращаются к ней (см. «Как оно устроено»).

## Шпаргалка: открыть агенту новый чат

Проще всего — в окне управления: ярлык **tg-agent** на рабочем столе (или
`bin\tgw.exe gui`) → вкладка «Чаты» → «Искать в Telegram» → выбрать права →
«Добавить».

То же из терминала:

```powershell
cd <tg-agent>

# 1. найти чат по куску названия (ссылка не нужна, видно и приватные, и архивные)
bin\tg.exe dialogs --filter "рабоч"

# 2. открыть доступ: без --send это только чтение
bin\tg.exe allow work-team --match "Рабочая группа" --send

# 3. проверить, что агент теперь видит
bin\tg.exe chats
```

Дальше агенту достаточно сказать словами: «посмотри, что нового в work-team»,
«найди в work-team про деплой», «напиши в work-team, что релиз готов». Алиас из
шага 2 — это и есть имя, которым он обращается к чату.

Поменять права у уже добавленного чата — та же команда без `--id`/`--match`.
Права задаются целиком: без `--send` отправка выключается.

```powershell
bin\tg.exe allow work-team --send          # чтение + отправка по кнопке
bin\tg.exe allow work-team --send --auto   # чтение + автоотправка с окном на отмену
bin\tg.exe allow work-team                 # только чтение
bin\tg.exe deny work-team                  # закрыть доступ совсем
```

Перезапускать ничего не нужно — файл перечитывается на каждом вызове.

Агент может и сам попросить доступ. Он видит твои папки Telegram и названия
чатов в них (`tg_list_folders`, `tg_folder_chats`; сообщений там нет) и шлёт
запрос (`tg_request_access`). В бот приходит карточка: какой чат, что нужно —
чтение или чтение и отправка — и зачем. Кнопки:

- **✅ Разрешить** — чат дописывается в `config/chats.toml` с алиасом из
  названия, заметкой «Открыт по запросу агента…» и запрошенными правами
  (автоотправки нет, каждое сообщение по-прежнему через карточку);
- **👁 Только чтение** — то же, но без отправки;
- **✋ Отказать** — белый список не меняется.

О решении агент узнаёт сам. Закрыть открытый так чат — `tg deny <alias>`.
Агентам из контейнеров папки и запросы недоступны.

## Установка

### 0. Сборка

Нужен Go (версию он подтянет сам по `go.mod`).

```powershell
powershell -ExecutionPolicy Bypass -File <tg-agent>\scripts\build.ps1
```

Скрипт прогоняет тесты и кладёт `tg.exe` и `tgw.exe` в `bin\`.

### 1. Ключи приложения

Зайти на https://my.telegram.org → **API development tools** → создать приложение.
Получишь `api_id` и `api_hash`. Вписать в `.env` (создать из `.env.example`):

```dotenv
TG_API_ID=1234567
TG_API_HASH=0123456789abcdef0123456789abcdef
TG_PHONE=+7...
```

Остальное в `.env` можно не трогать (часть настроек меняется в окне управления,
вкладка «Настройки»). Отдельного бота заводить не нужно: можно переиспользовать
бота, который уже шлёт тебе уведомления (например, о хуках Claude Code): по
умолчанию токен и chat_id читаются из
`~/.local/share/cc-telegram-notify/config.env` (`NOTIFICATIONS_BOT_TOKEN`,
`NOTIFICATIONS_CHAT_ID`). Другой путь — `TG_BOT_ENV_FILE`, либо впиши
`TG_BOT_TOKEN` и `TG_APPROVAL_CHAT_ID` прямо в `.env`.

### 2. Вход (один раз)

В окне управления: вкладка «Состояние» → «Получить код» → код из Telegram
(и пароль, если включена двухфакторка). Или в терминале:

```powershell
<tg-agent>\bin\tg.exe login
```

После этого в `data/session.json` лежит сессия — заново входить не нужно, даже
после перезагрузки.

> `data/session.json` = полный доступ к аккаунту. Не коммитить, не копировать,
> не отдавать. Отозвать: `bin\tg.exe logout` или в приложении Telegram →
> Настройки → Устройства (сессия называется `tg-agent`).

### 3. Белый список чатов

См. шпаргалку выше. Руками — в `config/chats.toml` (образец —
[`config/chats.example.toml`](config/chats.example.toml)):

```toml
[[chat]]
alias = "work-team"       # этим именем агент обращается к чату
id = -1001234567890       # id из `tg dialogs`; годится и "@username", и "me"
title = "Рабочая группа"
read = true               # можно читать
send = false              # писать нельзя
# auto_send = true        # вместе с send = true: без кнопки, с окном на отмену
note = "Только чтение задач"
```

Проверить настройку целиком:

```powershell
<tg-agent>\bin\tg.exe doctor
```

### 4. Подключить MCP-сервер к Claude Code

Для всех проектов (user scope):

```powershell
claude mcp add --scope user telegram -- <tg-agent>/bin/tg.exe mcp
```

Только в одном проекте — положить рядом с проектом `.mcp.json` (образец:
[`.mcp.json.example`](.mcp.json.example)).

Проверить: в сессии Claude Code выполнить `/mcp` — должен быть сервер `telegram`
со статусом connected.

### 5. Служба в автозапуск

```powershell
powershell -ExecutionPolicy Bypass -File <tg-agent>\scripts\install-task.ps1
```

Ставит задачу Планировщика `tg-agent` (`bin\tgw.exe serve`): запуск при входе в
систему, перезапуск после сбоя, без окна консоли. Служба держит постоянное
соединение с Telegram, ведёт ленты новых сообщений в реальном времени,
разбирает нажатия кнопок в боте и досылает автоотправку в срок. Агенты, CLI и
окно управления ходят в Telegram через неё — быстро, без переподключения на
каждый вызов.

Без службы тоже работает, но хуже: каждый вызов заново подключается к
Telegram, лент в реальном времени нет, а нажатие кнопки обрабатывается, только
пока какой-нибудь агент ждёт решения (или выполни `tg approvals --once`).
`tg doctor` и окно показывают, запущена ли служба.

### Обновление

```powershell
powershell -ExecutionPolicy Bypass -File <tg-agent>\scripts\build.ps1
```

Прогоняет тесты, собирает и перезапускает службу. Агентов останавливать не
нужно: их MCP-прослойка замечает новую сборку сама. Открытое окно управления
открыть заново.

## Команды владельца

```
tg gui                       окно управления (tgw.exe gui — без консоли)
tg login                     вход и сохранение сессии
tg logout                    отозвать сессию на стороне Telegram
tg whoami                    под каким аккаунтом работаем
tg dialogs [--filter x]      все диалоги (вкл. архив) — искать чат по имени
tg allow <alias> --match x   найти чат по имени и добавить в белый список
tg allow <alias> --id -100…  то же, но по готовому id
tg allow <alias> [--send [--auto]] [--no-read]   поменять права
tg deny <alias>              убрать чат из белого списка
tg chats [--status]          что разрешено агентам (+ непрочитанные)
tg read <alias> [--limit N] [--search x]
tg drafts [--status pending] очередь черновиков от агентов
tg pending                   что ждёт нажатия кнопки
tg serve                     служба (её запускает Планировщик)
tg approvals --once          разобрать накопившиеся нажатия, если службы нет
tg approve <id> [--send]     подтвердить отправку
tg reject <id>               отменить черновик
tg send <id>                 отправить подтверждённый черновик вручную
tg watch <alias> [--after N]  подписка: «alias id» на каждое новое сообщение
tg feeds [--poll]            состояние лент новых сообщений
tg doctor [--offline]        проверить конфигурацию
tg mcp                       MCP-сервер (его запускает Claude Code)
tg t3 …                      окружения T3 в контейнерах и треды шлюза (tg t3 help)
tg agents [--new-token]      агенты из контейнеров: MCP по HTTP
tg --profile <имя> init      заготовка профиля (второй аккаунт)
tg --profile <имя> <команда> любая команда в профиле (или TG_PROFILE=<имя>)
```

Все запускаются как `<tg-agent>\bin\tg.exe <команда>`. Изнутри сессии Claude
Code удобно префиксом `!` — команда выполнится от тебя, а не от агента.

## Как выглядит отправка сообщения

1. Агент вызывает `tg_draft_message`. Ничего не уходит, но тебе в бот прилетает
   карточка:

   > 🤖 **Агент просит отправить сообщение**
   > Чат: **Рабочая группа** (`work-team`)
   > Повод: отчёт о деплое из проекта my-service
   >
   > ───
   > **Деплой прошёл**, версия `1.4.2`
   > [ ✅ Отправить ] [ ✋ Отклонить ]

   Шапка отделена разделителем, а под ним — сообщение уже отрисованным, ровно
   так, как уйдёт. Агенты пишут в Markdown, отправка идёт через rich messages:
   заголовки, списки, таблицы, цитаты, блоки кода рисуются в чате как есть, и
   от твоего аккаунта тоже. Если сервер rich-формат не примет, сообщение уйдёт
   обычной markdown-разметкой (в аудите `format: markdown_fallback` и причина).
   `format="plain"` — текст без разметки.

2. Жмёшь кнопку (в боте или в окне управления, вкладка «Черновики» — там же
   текст можно поправить до отправки, карточка в боте обновится).
   - **Отправить** — сообщение уходит от твоего аккаунта, карточка тут же
     переписывается на «✅ Отправлено в «Рабочая группа» в 18:42 (id 10235)».
   - **Отклонить** — «✋ Отклонено», ничего не ушло.

3. Агент видит результат через `tg_wait_approval` и работает дальше. Если ты не
   нажал за `TG_APPROVAL_TIMEOUT_SEC` (10 минут), агент получает `waiting` и не
   висит дальше — карточка при этом остаётся живой, нажатие сработает и через час.

### Автоотправка

В чате с `auto_send = true` подтверждать не нужно. Черновик сразу получает
статус `scheduled` и уходит сам через `TG_AUTO_SEND_DELAY_SEC` (30 с). До этого
агент может отозвать его через `tg_cancel_draft`, а ты — кнопкой «✋ Отменить»
под карточкой или в окне управления. Если всё и так хорошо, «✅ Отправить
сейчас» отправит сразу, не дожидаясь окна. Отправку по таймеру делает служба (а
если её нет — отдельный процесс `tgw send-due`); захват черновика идёт под
локом очереди, так что он уйдёт ровно один раз.

Включать и выключать автоотправку можно прямо в боте: команда **/auto**
присылает список чатов, куда агентам разрешено писать (🟢 — автоотправка,
⚪ — по кнопке), нажатие переключает чат и сразу правит `config/chats.toml`
(при нескольких аккаунтах — чаты всех, кто делит бот, у чужих —
`<аккаунт>/<alias>`). **/notes** — заметки к аккаунтам: список, ➕ добавить
(текст — следующим сообщением), 🗑 убрать; то же короче — `/note <аккаунт>
<текст>` (при одном аккаунте — `/note <текст>`). Агенты видят заметки в
`tg_list_chats` и сами могут их оставлять (`tg_account_note`); в окне
управления — вкладка «Заметки». Команды бот принимает только от тебя. Поскольку служба теперь читает и
сообщения боту, а не только нажатия, боту подтверждений лучше быть отдельным
(свой токен в `.env`: `TG_BOT_TOKEN`), а не общим с уведомлениями
`cc-telegram-notify`.

### Файлы

Если агент прикладывает файлы, они приходят в бот прямо перед карточкой — так
же, как уйдут, — а в шапке карточки перечислены с размерами. Файлы больше 50 МБ
бот показать не может (ограничение Bot API) — в карточке у них пометка «не
показан». Картинки jpg/png уходят фото (видны в ленте, Telegram их пережимает),
остальное — документами без пережатия; картинку файлом агент шлёт с
`as_files=true`. При создании черновика с них
снимается копия, и после нажатия уходит именно она — агент не может подменить
файл между твоим одобрением и отправкой. Файлы из папки tg-agent, `.env`, ключи
и сессии к отправке не принимаются вовсе. Пределы — `TG_MAX_FILE_MB` (отправка)
и `TG_MAX_DOWNLOAD_MB` (скачивание) в `.env`.

Кнопки слушаешь только ты: нажатие с чужого user id отклоняется, попытка пишется
в аудит. Повторное нажатие на уже обработанной карточке ничего не делает.

Запасные пути, когда бот недоступен: окно управления, `tg pending` — что ждёт
решения, `tg approve <id> --send` — подтвердить и отправить из терминала,
`tg reject <id>` — отказать. `tg approvals --once` разбирает нажатия,
накопившиеся пока служба не работала (Telegram хранит их сутки).

Неподтверждённые черновики протухают через `TG_DRAFT_TTL_MIN` минут (по умолчанию 60).

### Режимы отправки (`TG_SEND_POLICY` в `.env`)

| Режим | Что требуется для отправки |
|---|---|
| `bot_approval` | кнопка под карточкой в боте (по умолчанию) |
| `human_approval` | команда `tg approve <id>` в терминале |
| `agent_confirm` | согласие в диалоге; агент передаёт его дословно |
| `disabled` | ничего, отправка выключена — только чтение |

Автоотправка (`auto_send`) работает в любом режиме, кроме `disabled`.

## Границы доступа

Что агент **не может**:

- прочитать или найти чат, которого нет в `config/chats.toml`;
- получить список всех твоих диалогов (`tg dialogs` — только из CLI и окна, не из MCP);
- написать в чат с `send = false` или при `TG_SEND_POLICY=disabled`;
- отправить сообщение без подтверждения — кроме чатов с `auto_send`, где у
  него (и у тебя) есть окно на отмену;
- отправить файлы самого tg-agent, `.env`, ключи и сессии.

Что стоит держать в голове: прочитанное агентом попадает в контекст модели.
Для чатов с секретами лучше не давать доступ вовсе. И `.env`, и `data/` уже в
`.gitignore` — не выноси их в репозиторий.

## Агенты в контейнерах (окружения T3 Code)

Агент может жить не на этом ноутбуке, а в контейнере со своим сервером T3
Code (`t3 serve`, образ — `business-magic/ops/t3-agent`). Именованный канал
службы оттуда не виден, сессию Claude в контейнере через её входящий канал не
разбудить, а курсор сессии сервер T3 наружу не отдаёт. Поэтому для таких
агентов два отдельных механизма: инструменты — по HTTP, пробуждение — через
свои треды шлюза.

```
 ноутбук или сервер со службой                        контейнер (один на проект)
┌────────────────────────────────────────┐          ┌───────────────────────────────┐
│ служба tg-agent (tgw.exe serve)        │ HTTP API │ t3 serve — окружение T3        │
│  ├ одно соединение с Telegram          │ ───────▶ │  └ тред «TG: <чат>» ── claude  │
│  ├ ленты чатов (data/feeds)            │ thread.  │      (создаёт и будит служба)  │
│  ├ треды шлюза (data/t3-threads.json)  │ create / │                               │
│  │                                     │ turn.    │ Claude Code в треде            │
│  └ MCP по HTTP  127.0.0.1:8790/mcp ◀───┼──────────┤  └ MCP telegram (HTTP, токен)  │
└────────────────────────────────────────┘  bearer  └───────────────────────────────┘
        ▲ тот же для N контейнеров: в config/t3.toml — список окружений,
          в config/agents.toml — агенты с токенами и своими чатами
```

1. В чате новое сообщение — служба дописывает его id в ленту.
2. Если на чат подписано окружение, служба начинает ход в своём треде
   «TG: <название чата>» этого окружения (`thread.turn.start`) с
   уведомлением: alias, сколько новых, готовый `tg_read_chat(chat, after_id)`.
   Треда ещё нет — служба заводит его (`thread.create` в проекте окружения,
   режим full-access, модель из конфига); тред удалили или убрали в архив —
   заводит новый. Тред — один на пару (окружение, чат), его id лежит в
   `data/t3-threads.json`.
3. Агент в треде читает чат и отвечает теми же инструментами по HTTP.
   Ответ в чат уходит только черновиком: карточка «Агент bala просит
   отправить сообщение» и кнопка владельца — как у местных агентов.
4. Служба ждёт конца хода: опрашивает тред раз в 2,5 с, пока не появится
   ход с новым `turnId` в состоянии completed, error или interrupted, но не
   дольше `turn_timeout_sec`. Итог — в аудит (`agent_t3_turn`: состояние,
   длина ответа, ошибка). Пока ход идёт, новые сообщения копятся и приходят
   следующим ходом одним уведомлением.

### Настройка

1. Окружения — `config/t3.toml` (образец
   [`config/t3.example.toml`](config/t3.example.toml)): имя, `origin`
   сервера T3, модель и способ получить токен — команда выпуска pairing-кода
   (`pairing_cmd`, например `docker exec t3-bala t3 auth pairing create
   --json`), admin-токен сервера для `POST /api/auth/pairing-token`
   (`admin_token_env`, сам токен — в `.env`) или готовый токен файлом
   (`token_file`). Токен с правами только на треды служба выпускает сама,
   хранит в `data/t3-token-<имя>.json` и перевыпускает по 401.
   Проверить: `bin\tg.exe t3 check`.
2. Токен агента: `bin\tg.exe agents --new-token` → в `.env`
   `TG_AGENT_BALA_TOKEN=<токен>`.
3. Агенты — `config/agents.toml` (образец
   [`config/agents.example.toml`](config/agents.example.toml)): имя,
   `token_env`, `chats` (подмножество белого списка), `env` (окружение из
   t3.toml) и `[http] listen` (по умолчанию `127.0.0.1:8790`). Служба
   поднимет HTTP за полминуты, без перезапуска; `bin\tg.exe agents` и
   `doctor` покажут адрес и что не так.
4. MCP в Claude Code внутри контейнера (из PowerShell: Git Bash портит
   пути в аргументах `docker exec`):

   ```powershell
   docker exec t3-bala claude mcp add --scope user --transport http telegram `
       http://host.docker.internal:8790/mcp --header "Authorization: Bearer <токен агента>"
   docker exec t3-bala claude mcp list    # telegram: … (HTTP) - ✔ Connected
   ```

   `host.docker.internal` — это 127.0.0.1 хоста для контейнеров Docker
   Desktop на этой же машине. Контейнер на другой машине — адрес tailnet
   (`listen = "100.x.y.z:8790"`) или SSH-туннель; наружу в интернет порт не
   публиковать: токен идёт открытым HTTP.
5. Подписка: агент из контейнера вызывает `tg_subscribe(chat)` — служба
   будит тред шлюза в его окружении (`env` агента). Или владелец:
   `bin\tg.exe t3 subscribe bala saved`. Проверить окружение ходом:
   `bin\tg.exe t3 wake bala saved "Ответь одним словом: готов"` — заведёт
   тред, если его нет, дождётся конца хода и покажет ответ.

```
tg t3                              окружения и треды шлюза (без сети)
tg t3 check [окружение]            сервер, протокол, токен, проект, живы ли треды
tg t3 subscribe <окр> <alias> [--after N]
tg t3 unsubscribe <окр> [alias]    снять подписку (тред остаётся)
tg t3 wake <окр> <alias> [текст]   ход в треде шлюза и его итог
tg agents [--new-token]            агенты, их токены, чаты и адрес HTTP
```

### Что агенту из контейнера можно

- Только его чаты из `chats` — остальных для него нет, в том числе в
  `tg_list_chats`, черновиках и подписках.
- Те же инструменты, что у местных агентов, кроме файлов: `files` у
  `tg_draft_message` и `tg_download_file` указывали бы на диск шлюза, а не
  на его, — они отклоняются.
- Каждый вызов — в аудит (`mcp_http_call`, имя агента, инструмент, чат);
  действия — с полем `agent`; запросы с чужим токеном — `mcp_http_denied`
  (не чаще раза в минуту с адреса). Черновик подписан именем агента.
- Сменить токен или чаты — правкой `.env` / `agents.toml`: действует со
  следующего запроса.

### Ограничения

- В окружениях из t3.toml будятся только треды шлюза. Агент, который сам
  работает в другом треде контейнера и вызвал `tg_subscribe`, получит
  уведомления не к себе, а в тред «TG: <чат>»: найти его тред по сессии
  Claude нельзя, курсор сессии API T3 не отдаёт.
- Один ход за раз на тред. Если в треде шлюза уже идёт ход (владелец пишет
  туда сам), уведомление подождёт его конца.
- Модель ходов задаётся в t3.toml; модель субагентов T3 не задаёт.
- Текст ответа агента служба не пересылает никуда: он в треде T3, в аудит
  идёт только длина. Показать его — `tg t3 wake`.
- MCP по HTTP без сессий: уведомление `tools/list_changed` агенту в
  контейнере не приходит — новый список инструментов он увидит при
  следующем подключении (новая сессия Claude).
- Старый токен окружения при перевыпуске не отзывается (у него нет на это
  прав) — истечёт сам через 30 дней; у десктопа его отзывает CLI T3.
- API T3 внутреннее (alpha): проверено на 0.0.44, протокол 1. Другой
  протокол — окружение считается недоступным (`tg t3 check` скажет).
- Живые тесты: `go test -tags live -run LiveEnv ./internal/t3` (тред и ход
  на `T3_LIVE_ORIGIN`, токен из `T3_LIVE_TOKEN_FILE` или через
  `T3_LIVE_CONTAINER`) и `go test -tags live -run LiveHTTP
  ./internal/mcpserver` (Claude Code в контейнере ходит к MCP по HTTP).
  Треды тестов называются «TG: проверка …».

## Профили: второй аккаунт Telegram

Одна установка может обслуживать несколько аккаунтов. Основной профиль —
как раньше (`.env`, `config/`, `data/` в корне). Именованный живёт в
`profiles/<имя>/` со своими `.env`, `config/` (белый список, t3.toml,
agents.toml) и `data/` (сессия MTProto, черновики, аудит, токены T3, треды
шлюза). Профиль выбирается флагом `--profile <имя>` в любом месте команды
или переменной `TG_PROFILE=<имя>`.

```powershell
# 1. заготовка: profiles\work\.env (ключи приложения — из основного .env),
#    белый список с одним Избранным, пустой data\
bin\tg.exe --profile work init [--phone +7…]

# 2. вход: номер — из profiles\work\.env (TG_PHONE) или спросит; код придёт
#    в Telegram этого аккаунта, при двухфакторке спросит пароль
bin\tg.exe --profile work login

# 3. служба профиля — отдельная задача Планировщика tg-agent-work
powershell -ExecutionPolicy Bypass -File scripts\install-task.ps1 -Profile work

# 4. MCP для агентов ничего добавлять не нужно: сервер telegram видит и
#    этот аккаунт (чаты — «work/<alias>»)

# чаты, проверка, окно управления — так же, с --profile
bin\tg.exe --profile work allow team --match "Команда" --send
bin\tg.exe --profile work doctor
bin\tgw.exe --profile work gui
```

Два профиля одновременно:

- Службы разные: задачи `tg-agent` и `tg-agent-work`, именованные каналы
  разные сами (имя считается от каталога профиля; у основного оно прежнее).
  `scripts\build.ps1` перезапускает службы всех профилей.
- Бот подтверждений — общий, основного профиля: заготовка `init` ставит
  профилю `TG_SEND_POLICY=bot_approval` без своего `TG_BOT_TOKEN`
  (`Settings.SharedBot`). Карточки черновиков и запросов доступа профиль шлёт
  в тот же бот с пометкой «аккаунт work», в кнопках — метка `@work|…`.
  Апдейты бота слушает только основная служба: нажатие с меткой она передаёт
  службе профиля (операция `callback`; нет службы — `tg --profile work op
  callback`). Свой бот профилю — `TG_BOT_TOKEN` и `TG_APPROVAL_CHAT_ID` в
  `profiles\work\.env`; без бота вовсе — `TG_SEND_POLICY=human_approval` и
  `tg --profile work approve <id> --send`.
- MCP по HTTP: у профилей разные порты — в `profiles\work\config\agents.toml`
  `[http] listen = "127.0.0.1:8791"`. Агенту из контейнера виден только
  аккаунт своего MCP-сервера.
- Агенты: сервер `telegram` (любого профиля) видит все аккаунты
  (`mcpserver/route.go`). `tg_list_chats` отвечает по аккаунтам, чаты не
  основного — `<аккаунт>/<alias>`; вызов к такому чату уходит в службу его
  аккаунта (`accounts.Call`; службы нет — `tg --profile <аккаунт> op tool`).
  Черновики и запросы доступа по id ищутся по всем аккаунтам, папки и
  запросы доступа — с параметром `account`. Подписка на чат профиля живёт в
  службе профиля, будит ту же сессию; адрес сессии (`hello`) основная
  служба раздаёт остальным. Подписки, черновики и аудит у профилей не
  пересекаются. Отдельный сервер `telegram-work` больше не нужен (работает,
  но видит то же самое).
- Заметки к аккаунтам — общие, в `data/account_notes.json` основного
  профиля; чей аккаунт (имя и @username) служба профиля кэширует в
  `data/account.json`.

## Как оно устроено

```
cmd/tg/            точка входа: служба, MCP, CLI, окно — один бинарник
internal/
  service/         служба и её операции; Do — вызвать в службе или на месте
  svc/             канал до службы: named pipe только для своей учётной записи
  mcpproxy/        `tg mcp`: тонкая прослойка агента поверх службы
  mcpserver/       инструменты MCP — то, что видит агент; http.go — MCP по
                   HTTP для агентов из контейнеров (bearer-токен, свои чаты);
                   route.go — вызовы к чатам других аккаунтов
  accounts/        вызов операции в службе другого аккаунта (профиля)
  tgc/             MTProto (gotd): постоянное соединение службы с событиями
                   или прямое подключение на время запроса; чтение, отправка,
                   медиа, расшифровка, кэш access_hash, поправка часов
  core/            проверки прав, черновики, кнопки, автоотправка, ленты,
                   подписки; remote.go — треды шлюза в окружениях T3
  t3/              API T3 Code: десктоп (тред по сессии Claude) и окружения
                   (токены, thread.create, turn.start, ожидание хода);
                   t3test/ — сервер T3 в памяти для тестов
  config/          .env, белый список, t3.toml, agents.toml, профили
  outbox/          очередь черновиков data/outbox.json
  bot/             Bot API: карточки и кнопки, запасной маршрут через прокси
  gui/             окно управления: локальный HTTP + WebView2
  cli/             команды владельца
  lock/            межпроцессные локи на файлах
  chatsfile/       правка config/chats.toml без потери комментариев
  audit/           журнал data/audit.jsonl
scripts/
  build.ps1        тесты, сборка bin\tg.exe и bin\tgw.exe, перезапуск службы
  install-task.ps1 служба в Планировщик задач (-Profile <имя> — служба профиля)
config/
  *.example.toml   образцы chats.toml, t3.toml, agents.toml
```

**Служба.** В Telegram ходит один процесс — служба `tg-agent` (`tgw.exe
serve`). Она держит постоянное соединение: вызовы не тратят секунды на
подключение, а новые сообщения Telegram присылает сам (менеджер обновлений
gotd с восстановлением пропусков) — служба сразу дописывает их id в ленты. Раз
в минуту она ещё сверяет верхние сообщения чатов — страховка от пропусков.

**Канал.** Остальные процессы — MCP-прослойки агентов, CLI, окно управления —
вызывают операции службы через named pipe, доступный только твоей учётной
записи Windows. Если служба не запущена, та же операция выполняется на месте:
с прямым подключением к Telegram под файловым локом сессии.

**Обновление без перезапуска агентов.** MCP-сервер живёт, пока открыта сессия
Claude Code, поэтому `tg mcp` — прослойка без логики: вызовы уходят в службу
(а без неё — в свежий `bin\tg.exe`), и по метке сборки в ответах службы она
замечает обновление и перечитывает список инструментов.

**Кнопки бота.** Апдейты бота Telegram отдаёт ровно одному потребителю, поэтому
`getUpdates` берётся под локом `data/bot-updates.lock`. Обычно его держит
служба; если её нет, роль на время ожидания берёт сам агент.

Часы компьютера могут расходиться с серверными: MTProto отвергает клиента при
расхождении больше ~30 с, поэтому сдвиг измеряется по `api.telegram.org` и
учитывается автоматически.
