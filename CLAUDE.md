# tg-agent

Проект даёт агентам Claude Code доступ к Telegram владельца, ограниченный белым
списком чатов.

- Правила работы с Telegram для агента: **[AGENTS.md](AGENTS.md)** — читать перед
  первым вызовом любого `tg_*` инструмента.
- Установка, команды владельца, устройство: [README.md](README.md).

Работая над кодом этого проекта:

- Go. Сборка — только `scripts\build.ps1` (тесты + `bin\tg.exe` и `bin\tgw.exe`
  без консоли); запущенные exe он не перезаписывает, а переименовывает в `*.old.exe`.
- `.env`, `data/` (сессия, аудит, черновики) и `config/chats.toml` — приватные,
  не коммитить, не показывать в выводе, не копировать в другие места (в том
  числе во временные папки для тестов).
- Любое ослабление проверок в `internal/core` (белый список, подтверждение
  отправки, автоотправка, проверка чужих нажатий) и в `internal/attach` (фильтр
  секретов) — только по прямой просьбе владельца.
- Токен бота берётся из чужого `config.env` (`cc-telegram-notify`) — не копируй
  его в этот репозиторий и не печатай в выводе (ошибки HTTP вычищаются от
  токена в `bot.scrub`).
- Устройство: служба `bin\tgw.exe serve` (задача Планировщика `tg-agent`,
  `internal/service`) держит единственное постоянное соединение с Telegram,
  пишет ленты по событиям, разбирает кнопки бота и досылает автоотправку.
  Остальные процессы (MCP-прослойки агентов, CLI, окно) вызывают её операции
  через named pipe (`internal/svc`, `service.Do`); без службы та же операция
  выполняется на месте с прямым подключением. Всё, что ходит в Telegram из
  CLI и окна, — только через `service.Do`: прямой `tgc.Run` при запущенной
  службе вернёт `ServiceOwned`.
- `scripts\build.ps1` вводит сборку в работу сам: перезапускает службу, а
  MCP-серверы агентов перезапускать не нужно — `tg mcp` лишь прослойка
  (`internal/mcpproxy`): вызовы уходят в службу (без неё — в свежий
  `bin\tg.exe tool-call`), а новую сборку она замечает по метке и
  перечитывает список инструментов (`tools/list_changed`). Логику держать в
  `internal/core` и инструментах, а не в прослойке: её код обновляется только
  с новой сессией.
- `tgw.exe serve` — надзиратель (`service.Supervise`): запускает рабочий
  процесс `serve --worker`, поднимает его после падения (`service_crashed` в
  аудите) и пишет его вывод, включая трассировки паник, в `data/service.log`.
  Рабочий привязан к job object и умирает вместе с надзирателем. Зависшее
  соединение gotd служба пересоздаёт сама (сторож в `tgc/shared.go`,
  `service_stalled`).
- Подписки агентов (`tg_subscribe`, `core/subscribe.go`): служба будит сессию
  Claude Code через её входящий канал (`internal/inbox`, cross-session
  messaging). Адрес и токен канала есть только в окружении потомков сессии —
  их передаёт прослойка (`ToolArgs.Agent` и `hello` раз в минуту); сессия
  ищется по `CLAUDE_CODE_SESSION_ID`. В уведомлении только alias и id, без
  текста сообщений.
- T3 Code сам останавливает процесс Claude у треда, простоявшего 30 минут
  (`ProviderSessionReaper`), — канала сессии больше нет. Запасной путь
  (`internal/t3`): тред ищется по id сессии в `~/.t3/userdata/state.sqlite`
  (`provider_session_runtime.resume_cursor_json.$.resume`), ход запускается
  через API T3 (`thread.turn.start`). Токен с правами только на треды служба
  выпускает сама (`auth pairing create` + `/oauth/token`), хранит в
  `data/t3-token.json` и обновляет. Нет T3 или он не отвечает — путь просто
  выключен (`t3.Unavailable`), остальное работает. Живой тест:
  `go test -tags live -run Live ./internal/t3` (будит свой же тред).
- Перезапуск службы руками: `Stop-ScheduledTask` НЕ убивает процесс —
  добивать `tgw.exe` с `serve` в командной строке через `Stop-Process`, потом
  `Start-ScheduledTask` (или `scripts\install-task.ps1`). Локи убитых процессов
  снимаются сами (проверка, жив ли pid-владелец и не занят ли его pid другим
  процессом). Если службу убили между нажатием «Отправить» и отправкой,
  новая при старте дошлёт такой черновик сам (`RecoverInterrupted`).
- Автоотправку в срок делает служба; если её нет — отдельный процесс
  `tgw send-due`, который запускает `tg_draft_message`.
- Живые тесты: `go test -tags live -run Live ./internal/core` (нужна служба).
- Открытое окно управления крутит старую сборку до повторного открытия.
- Живые проверки с Telegram — только на чате `saved` (Избранное): это песочница.
- Id карточки брать из черновика (`bot_message_id`): под rich-сообщением
  callback приходит без `message`. Id сообщений в личке у бота и у
  пользовательского аккаунта разные — искать карточку со стороны MTProto по
  содержимому, а не по id.
- Часы этого компьютера спешат примерно на полминуты: MTProto без поправки
  (`tgc/clock.go`) отвергает клиента с «msg_id too high».
