# tg-agent

Проект даёт агентам Claude Code доступ к Telegram владельца, ограниченный белым
списком чатов.

- Правила работы с Telegram для агента: **[AGENTS.md](AGENTS.md)** — читать перед
  первым вызовом любого `tg_*` инструмента.
- Установка, команды владельца, устройство: [README.md](README.md).

Работая над кодом этого проекта:

- Законченную работу коммитить самому, не спрашивая. Обкатанный коммит —
  тесты прошли, сборка в работе, изменение проверено вживую — сразу и
  пушить: его можно отдавать пользователям. Не обкатан — только коммит, и
  сказать, чего не хватает.
- Go. Сборка — только `scripts\build.ps1` (тесты + `bin\tg.exe` и `bin\tgw.exe`
  без консоли); запущенные exe он не перезаписывает, а переименовывает в `*.old.exe`.
- `.env`, `data/` (сессия, аудит, черновики) и `config/chats.toml` — приватные,
  не коммитить, не показывать в выводе, не копировать в другие места (в том
  числе во временные папки для тестов).
- Любое ослабление проверок в `internal/core` (белый список, подтверждение
  отправки, автоотправка, проверка чужих нажатий) и в `internal/attach` (фильтр
  секретов) — только по прямой просьбе владельца.
- Токен бота берётся из чужого `config.env` (`cc-telegram-notify`) — не копируй
  его в этот репозиторий и не печатай в выводе (ошибки HTTP вычищаются от
  токена в `bot.scrub`).
- Устройство: служба `bin\tgw.exe serve` (задача Планировщика `tg-agent`,
  `internal/service`) держит единственное постоянное соединение с Telegram,
  пишет ленты по событиям, разбирает кнопки бота и досылает автоотправку.
  Остальные процессы (MCP-прослойки агентов, CLI, окно) вызывают её операции
  через named pipe (`internal/svc`, `service.Do`); без службы та же операция
  выполняется на месте с прямым подключением. Всё, что ходит в Telegram из
  CLI и окна, — только через `service.Do`: прямой `tgc.Run` при запущенной
  службе вернёт `ServiceOwned`.
- `scripts\build.ps1` вводит сборку в работу сам: перезапускает службу, а
  MCP-серверы агентов перезапускать не нужно — `tg mcp` лишь прослойка
  (`internal/mcpproxy`): вызовы уходят в службу (без неё — в свежий
  `bin\tg.exe tool-call`), а новую сборку она замечает по метке и
  перечитывает список инструментов (`tools/list_changed`). Логику держать в
  `internal/core` и инструментах, а не в прослойке: её код обновляется только
  с новой сессией.
- `tgw.exe serve` — надзиратель (`service.Supervise`): запускает рабочий
  процесс `serve --worker`, поднимает его после падения (`service_crashed` в
  аудите) и пишет его вывод, включая трассировки паник, в `data/service.log`.
  Рабочий привязан к job object и умирает вместе с надзирателем. Зависшее
  соединение gotd служба пересоздаёт сама (сторож в `tgc/shared.go`,
  `service_stalled`).
- Подписки агентов (`tg_subscribe`, `core/subscribe.go`): служба будит сессию
  Claude Code через её входящий канал (`internal/inbox`, cross-session
  messaging). Адрес и токен канала есть только в окружении потомков сессии —
  их передаёт прослойка (`ToolArgs.Agent` и `hello` раз в минуту); сессия
  ищется по `CLAUDE_CODE_SESSION_ID`. В уведомлении только alias и id, без
  текста сообщений. Правки и удаления уже известных агенту сообщений
  (`tgc.Events.Edit/Delete` → `noteChange`) копятся в подписке (`Edited`,
  `Deleted`) и уходят тем же уведомлением; правками считаются только видимые
  (`visibleEdit`: есть edit_date, нет edit_hide). Удаления в личках и
  обычных группах приходят без чата — чат ищется по лентам. Реакции в
  личках и обычных группах Telegram шлёт как правку с прежней edit_date —
  поэтому правка новая, только если edit_date сменилась (`tgc/edits.go`,
  даты правок — `data/edit_dates.json`), а без известной прежней — если она
  моложе 15 минут или позже прошлой остановки службы (там же отметка
  `alive`). Отметка обновлений gotd — на диске (`tgc/updstate.go`,
  `data/updates_state.json`): после перезапуска служба догоняет правки и
  удаления за время простоя через getDifference; слишком долгий простой —
  `updates_too_long` в аудите, остаётся сверка лент. Чат (в форуме — тему;
  весь чат пересекается с любой темой) слушает одна сессия: занят живой
  сессией другого треда — отказ с именем треда (`t3.ThreadInfo`), забрать —
  `takeover` по слову владельца; у сессии с `Dead` или из закрытого треда
  подписка переходит сама (`agent_subscription_taken` в аудите).
- T3 Code сам останавливает процесс Claude у треда, простоявшего 30 минут
  (`ProviderSessionReaper`), — канала сессии больше нет. Запасной путь
  (`internal/t3`): тред ищется по id сессии в базе десктопа (`t3.ThreadOf`).
  С 16.10.2026 T3 на протоколе оркестрации 2 (`t3/v2.go`): база
  `statev2.sqlite` (`orchestration_v2_projection_provider_threads`,
  `$.nativeThreadRef.nativeId`; сессии до переезда — в
  `provider_session_runtime`), HTTP API только читает, сообщение в тред —
  `message.dispatch` по WebSocket `/ws` (RPC Effect, тикет
  `/api/auth/websocket-ticket`) с `deliveryIntent: "steer"`: в идущий ход
  сразу, иначе новый ход. Протокол 1 (`state.sqlite`, `thread.turn.start`)
  оставлен. T3 может завести треду новую сессию Claude (при переезде на v2
  сменились у всех) — подписки сессий одного треда служба сводит к его
  текущей (`joinThreadSubs`, `agent_subscription_moved` в аудите). Окружения
  из `config/t3.toml` пока умеют только протокол 1. Токен с правами только на треды служба
  выпускает сама (`auth pairing create` + `/oauth/token`), хранит в
  `data/t3-token.json` и обновляет. Нет T3 или он не отвечает — путь просто
  выключен (`t3.Unavailable`), остальное работает. Живой тест:
  `go test -tags live -run Live ./internal/t3` (будит свой же тред).
- Агенты в контейнерах (README, «Агенты в контейнерах»). Инструменты — по
  HTTP (`mcpserver/http.go`, служба слушает по `config/agents.toml`), у
  вызова `s.Agent != nil`, а белый список в `s` уже урезан до чатов агента
  (`config.Settings.Restrict`). Правила для нового кода:
  - инструмент получает настройки только через `load(ctx)` / `run` в
    mcpserver — иначе агент из контейнера увидит весь белый список;
  - всё, что касается чата, — через `readable` / `sendable` (`s.Resolve`):
    урезание держится на них; черновики — через `visibleDraft`;
  - аудит действий агента — `logEvent(s, …)`, а не `audit.Log`: так в
    записи есть имя агента;
  - всё, что читает или пишет файлы на диске шлюза по просьбе агента
    (вложения, скачивание), для `s.Agent != nil` отклонять;
  - токены агентов сравнивать `subtle.ConstantTimeCompare`, не печатать и
    не писать в аудит; `DisableLocalhostProtection` держится только на
    обязательном bearer-токене.
- Окружения T3 из `config/t3.toml` (`core/remote.go`, `t3/env.go`): там служба
  будит только свои треды «TG: <чат>» (`data/t3-threads.json`), по сессии
  Claude их не найти — курсор API не отдаёт. Работа с T3 — только через
  `t3.Env`: после `thread.turn.start` конец хода определять по новому
  `turnId` (снимок какое-то время показывает прошлый ход), а не по одному
  `state`; `bootstrap.createThread` не использовать (500 «Thread does not
  exist»). Новый ход — только когда прошлый кончился (`remoteRun.busy`,
  `t3.Busy`). Тесты — на `t3test.Fake`; живые — `go test -tags live -run
  LiveEnv ./internal/t3` и `-run LiveHTTP ./internal/mcpserver` на
  контейнере `t3-bala` (его не останавливать и не пересоздавать; треды
  тестов — с заголовком «TG: …»).
- Профили (`config/profile.go`): каталоги только через `config.Home()`,
  `DataPath()`, `ConfigDir()`, `EnvPath()`, `ChatsFile()` или методы
  `Settings`; `config.Root` — это установка (bin/, AGENTS.md, scripts/), не
  данные. Дочерние процессы получают профиль через `TG_PROFILE`, рабочий
  процесс службы — ещё и флагом `--profile` (по нему install-task.ps1
  отличает службы профилей). Основной профиль менять нельзя: его пути и имя
  канала службы прежние (тест `TestAddressDefaultProfileUnchanged`).
  Сессию основного профиля (`data/session.json`) не трогать и не
  перелогинивать.
- Несколько аккаунтов (`config/accounts.go`, `mcpserver/route.go`): аккаунт =
  профиль (`main` — основной, остальные — `profiles/*` с `.env`). Профиль —
  глобальное состояние процесса, поэтому чужой аккаунт обслуживает только
  его служба: промежуточный слой MCP `route` передаёт туда вызовы
  (`accounts.Call` → `svc.CallAt`, без службы — `tg --profile X op tool`)
  с `ToolArgs.Local` (там не маршрутизировать, иначе tg_list_chats
  зациклится). Агенту чаты не основного аккаунта видны как
  `<аккаунт>/<alias>` — всё, что уходит агенту с alias, — через `s.Ref`;
  `Resolve` принимает и ссылку со своим аккаунтом. Пока аккаунт один, всё
  как раньше (`config.Multi()`); агентам из контейнеров маршрутизации нет.
  Бот общий: профиль без своего бота (`SharedBot`) шлёт карточки ботом
  основного с меткой `@<профиль>|` в callback_data, getUpdates у него не
  крутится (`ownsUpdates`, `Pump`), а основная служба отдаёт такие нажатия
  его службе (`passCallback`, op `callback`). Заметки к аккаунтам
  (`core/notes.go`) — один файл на установку, `data/account_notes.json`
  основного профиля, под локом.
- Темы форумов (`tgc/topics.go`): тема = id её служебного сообщения, General
  = 1. Тема сообщения — `TopicOf` (forum_topic → reply_to_top_id или
  reply_to_msg_id), настоящий ответ — `ReplyID` (в теме без top_id
  reply_to_msg_id — сама тема, не ответ). Чтение темы — `messages.getReplies`
  (General — отбор из общей ленты), отправка — `Target.Topic` → `replyTo`.
  Черновик хранит тему (`Draft.Topic`), её берёт из `reply_to`, если не
  задана. Подписка с темой (`subscription.Topics`) отбирает новые и правки
  через `topicsOf` (запрос сообщений по id, память `topicMemo`). Белый список
  — на чат целиком.
- Расшифровка голосовых (`internal/stt`, программа `stt/` → `bin\tgstt.exe`):
  русская речь — GigaAM v3 через sherpa-onnx (cgo, свой Go-модуль в `stt/`,
  чтобы основной оставался без cgo; DLL рядом с exe кладёт build.ps1),
  язык определяет whisper base, длинное режет Silero VAD; не русская —
  Telegram. Модели — `stt/models` (`scripts\install-stt.ps1`). Служба держит
  один процесс tgstt (JSON-строки в stdin/stdout, логи — в stderr →
  `data/service.log`), запросы по одному, после 15 минут простоя он
  закрывается. Голосовое для неё качается в `downloads/<alias>`, модель
  гоняется вне `tgc.Run`, где можно. Кэш `transcripts.json` хранит движок
  (`{text, engine, language}`; старые строки — Telegram, их при GigaAM
  переделываем), агент видит `transcript_engine`. Нет tgstt или моделей,
  или `TG_STT=off` — только Telegram. Python не нужен.
- Папки и запросы доступа (`core/access.go`, `tgc/folders.go`): агент видит
  папки и названия чатов вне белого списка (только список, без сообщений) и
  просит доступ карточкой (callback `a:<id>:rw|r|no`). Белый список меняется
  только нажатием владельца (`grantAccess` → `chatsfile`); агенту из
  контейнера всё это закрыто (`onlyLocal`). Полный обход диалогов кэшируется
  на минуту (`dialogsFresh`) — иначе FLOOD_WAIT.
- Бот подтверждений принимает и сообщения владельца (`core/botmenu.go`):
  `/auto` — переключатели автоотправки (callback `s:<alias>`, меню —
  обычное сообщение, не rich, чтобы нажатие пришло с id меню). Смещение
  апдейтов хранится вместе с id бота (`bot_offset.json`): при смене токена
  оно сбрасывается, иначе новый бот терял бы нажатия.
- Перезапуск службы руками: `Stop-ScheduledTask` НЕ убивает процесс —
  добивать `tgw.exe` с `serve` в командной строке через `Stop-Process`, потом
  `Start-ScheduledTask` (или `scripts\install-task.ps1`). Локи убитых процессов
  снимаются сами (проверка, жив ли pid-владелец и не занят ли его pid другим
  процессом). Если службу убили между нажатием «Отправить» и отправкой,
  новая при старте дошлёт такой черновик сам (`RecoverInterrupted`).
- Автоотправку в срок делает служба; если её нет — отдельный процесс
  `tgw send-due`, который запускает `tg_draft_message`.
- Живые тесты: `go test -tags live -run Live ./internal/core` (нужна служба).
- Открытое окно управления крутит старую сборку до повторного открытия.
- Живые проверки с Telegram — только на чате `saved` (Избранное): это песочница.
  Для проверок между аккаунтами — группа «111» (в архиве): основной аккаунт
  и work, alias `111-chat` (основной, чтение) и `work/111-chat` (work,
  отправка через карточку).
- Упоминания (`tgc/mentions.go`, `core/mentions.go`): человека без username
  агент упоминает ссылкой `[Имя](tg://user?id=…)`. Сам Telegram в rich-markdown
  делает из неё упоминание только для «знакомых» без access_hash (себя,
  контакты), участника группы молча выбрасывает. Поэтому такой текст служба
  разбирает руками сервера в черновик Избранного (ссылки — на заглушку,
  прежний черновик возвращается) и шлёт готовые блоки: заглушки →
  `TextMentionName`, access_hash — в `users` (`tgc/richmention.go`, и для
  правки). Не вышло — запасной разбор markdown с `InputMessageEntityMentionName`.
  «@Имя», которое не может быть username, служба сама заменяет упоминанием
  по id, если среди недавних авторов чата он один; иначе оставляет текстом и
  пишет агенту в `mentions` ответа. «@» — только в начале слова (почта не
  задевается). Отказов нет. В чтении — `mentions`, `mentioned`, у чата
  `unread_mentions`.
- Слежение за обновлениями для клиента MAX (`internal/upstream`,
  `core/upstream.go`): служба основного профиля раз в час проверяет
  web.max.ru (`/_app/version.json`; при новой сборке — `appVersion` рядом с
  адресом WebSocket в её скриптах), каталог `hashes.pymax.org` и PyMax на
  GitHub (релиз, коммиты, отметка правок протокола и входа). Состояние —
  `data/upstream.json`. Изменение — карточка в бот, закреплённая до «✅
  Разобрано» (callback `u:ack`); не удалось отправить — не запоминается.
  Новая карточка источника заменяет его неразобранную: та откреплена, без
  кнопки, с пометкой (закреплённые — `data/upstream_cards.json`).
  Первая проверка источника — только сводка; `/updates` — проверить сейчас.
  Закрепление — для внимания владельца: проверив карточку и не найдя, что
  требует его решения, агент сам снимает её — `bin\tg.exe updates ack
  <источник|all> "<вывод>"` (откреплена, без кнопки, вывод дописан в неё;
  `tg updates` — какие висят). Требует — оставить закреплённой и сказать.
  Живая проверка источников: `go test -tags live -run Live ./internal/upstream -v`.
- Клиент MAX (`internal/maxc`, команды `tg max`): режим веб-клиента —
  WebSocket `wss://api.oneme.ru/websocket` с Origin `https://web.max.ru`,
  кадры как у TCP (`>BBHHI` + msgpack; входящие сжаты: flags 0xFF — zstd,
  иначе ненулевые — блок LZ4), протокол сверен с PyMax. Расширение msgpack
  типа 1 — обёрнутое значение, `unwrapExt` разворачивает его сразу после
  распаковки, незнакомые расширения — nil. Пишет в WebSocket один писатель
  под замком, события — в порядке прихода из одной горутины. Вход: SESSION_INIT
  → GET_QR / QR_STATUS / LOGIN_BY_QR (облачный пароль — CHECK_PASSWORD, его
  вводит только владелец в консоли) → LOGIN по токену. Сессия —
  `data/max/session.json` (токен = полный доступ к аккаунту: не печатать, не
  в аудит), с тем же id устройства и user-agent, что при входе. Отозванный
  токен — `ErrTokenRevoked`: сам не перезаходить, сказать владельцу.
  `maxc.Client` держит вход и переподключается (пауза 1 с → 1 мин),
  `OnLogin` — после каждого входа (сверять пропущенное), `OnEvent` —
  `ParseEvent`: NOTIF_MESSAGE 128 со статусом EDITED/REMOVED — правка или
  удаление, 142 — удаление списком, 130 — прочтение. На свои действия из
  той же сессии сервер событий не шлёт. Вызовы: `History`, `Send` (cid — мс,
  строго растут; ответ — `link` REPLY), `Edit`, `Delete`. Живые проверки
  записи — только в «Избранном» MAX (чат 0): `go test -tags live -run
  LiveSaved ./internal/maxc -v`; соединение — `-run LiveSession`.
- Аккаунт MAX у агентов — профиль `max` с `TG_NETWORK=max`
  (`Settings.IsMAX`, ключи Telegram не нужны): маршрутизация `max/<alias>`,
  общий бот, черновики и подписки — те же, что у профилей Telegram. Служба
  такого профиля вместо `tgc.Serve` и сверки лент запускает `core.RunMax`
  (`core/max.go`): ленты и `noteChange` по событиям, после каждого входа —
  наверстать по истории; отозванная сессия — закреплённая карточка (раз).
  Ветки по сети — `ReadChat` (`maxReadChat`), `DeliverApproved`
  (`maxDeliver`), `EditMessage` (`maxEditOld`), op `dialogs`, `selfLabel`;
  `topicsOf` и подписка с темой для MAX не ходят в Telegram; поиск, папки,
  доступ, реакции, вложения и расшифровка — `core/max_media.go` (тем нет —
  `maxGuard` отказывает в `tg_list_topics`). Формы запросов, которых нет в
  PyMax (поиск 73, аудио 301, расшифровка 202/293, правила папок
  `FILTER_*`), взяты из скриптов web.max.ru. Разные виды вложений в одном
  сообщении сервер не принимает (`proto.payload`) — `maxDeliver` шлёт их
  отдельно. Файлы MAX — через `maxc.HTTP` (доверяет «Russian Trusted Root
  CA» только он). Соединение держит только служба:
  без неё `ErrNoMax`; `tg max status` при службе спрашивает её (op
  `max_status`), второе соединение с тем же токеном не открываем. Id
  сообщения MAX = мс<<16 | счётчик, больше 2⁵³: от Claude Code приходит
  округлённым (±8) — `maxFixID` / `maxNearestSent` находят точный. В
  «Избранном» MAX сообщения владельца будят подписку (своими считаются только
  отправленные шлюзом), в остальных чатах — нет.
- Правка отправленного (`core/edit.go`, `tg_edit_message`): только сообщения,
  ушедшие через tg-agent (черновик sent с этим message_id, у агента из
  контейнера — свой), и только `TG_EDIT_WINDOW_MIN` (60) минут после отправки.
  Правка — обычный черновик с `EditOf`/`EditOld`: тот же путь подтверждения
  (карточка «было → станет», кнопка «Исправить», автоотправка с окном),
  `DeliverApproved` вызывает `messages.editMessage` (`tgc.EditMessage`).
  Меняется только текст. В Избранном своё приходит без `out`.
- Id карточки брать из черновика (`bot_message_id`): под rich-сообщением
  callback приходит без `message`. Id сообщений в личке у бота и у
  пользовательского аккаунта разные — искать карточку со стороны MTProto по
  содержимому, а не по id.
- Часы этого компьютера спешат примерно на полминуты: MTProto без поправки
  (`tgc/clock.go`) отвергает клиента с «msg_id too high».
